# Техническое Задание: D&D 5e Encounter Tracker & Bestiary

## 1. Концепция и Бизнес-логика
Приложение для Мастеров Игры (ГМов) в D&D 5e. Позволяет искать статблоки монстров через публичный API, кэшировать их в локальную базу (офлайн-режим) и управлять боевыми столкновениями (энкаунтерами) с трекингом инициативы и здоровья.

## 2. Технологический стек
*   **Стейт-менеджмент:** `flutter_bloc` + пакет `bloc_concurrency`. Под каждую вкладку (фичу) создается свой независимый BLoC/Cubit.
*   **Сетевой слой:** `dio` + `retrofit` (генерация API-клиента). Использование `json_serializable` / `freezed` для моделей.
*   **Локальная БД:** `isar` или `sqflite`.
*   **Многопоточность:** Обязательное использование изолятов (`Isolate.run()`).
*   **Локализация и Темизация:** `slang` (для i18n), кастомный `ThemeExtension`.
*   **Нативная интеграция:** `flutter_native_splash` (сплеш-скрин), `flutter_launcher_icons` (иконки приложения).

## 3. Архитектура (DDD - Domain-Driven Design)
Приложение строго разделяется на слои. Запрещено передавать объекты одного слоя в другой без маппинга.

1.  **DTO (Data Transfer Object):** Слой сети. Сырые классы, сгенерированные из JSON-ответов API. Завязаны на контракты бэкенда.
2.  **Entity (Модель БД):** Слой локального хранения. Содержит аннотации для Isar/SQLite (индексы, связи).
3.  **Domain Model (Доменная / Бизнес-модель):** Чистый Dart-класс. UI-слой ничего не знает про DTO или Entity, он работает только с доменной моделью.
4.  **Repository (Репозиторий):** Фасад, скрывающий источник данных. Место, где DTO/Entity маппятся в Domain Model.
5.  **UseCase (Интерактор):** Слой бизнес-логики. Сюда выносится сложная логика (например, `RollInitiativeUseCase`, `SyncBestiaryUseCase`), чтобы не раздувать BLoC. BLoC должен остаться тупым транслятором UI-эвентов в стейт.

## 4. Навигация и Роутинг

**Фаза 1: Ручное управление (Изучение Core-механик)**
*   Отсутствие сторонних пакетов роутинга.
*   **Сохранение состояния:** Использование `IndexedStack` для корневых вкладок.
*   **Вложенная навигация:** Использование локальных `Navigator` виджетов внутри каждой вкладки `IndexedStack`, чтобы при переходе от списка к деталям монстра на мобилках не исчезал `BottomNavigationBar`.

**Фаза 2: Рефакторинг на go_router (Оптимизация)**
*   Перенос логики на декларативный `go_router`.
*   Замена `IndexedStack` на `StatefulShellRoute`.
*   Сравнение подходов и выявление профита в удобстве передачи аргументов и обработке Deep Links.

## 5. Функциональные модули

### 5.1. Инициализация (Сплеш-скрин)
*   **Требования:** Нативная реализация через `flutter_native_splash` (xml/storyboard), закрывающая белое окно загрузки движка. После инициализации DI-контейнера и локальной БД сплеш снимается программно.

### 5.2. Бестиарий (Глобальный справочник)
*   **Функционал:** API Open5e. Пагинация, локальный текстовый поиск с дебаунсом (300-500мс), фильтрация (CR, тип).
*   **Слепая зона (Оптимизация):** Парсинг JSON-ответов размером 1-2 МБ с вложенными массивами заблокирует Main Thread. Обязательно выносить десериализацию в `Isolate.run()`.
*   **Слепая зона (Стейт):** При новом поиске необходимо сбрасывать счетчик пагинации и очищать старый кэш в стейте BLoC-а.

### 5.3. Избранное (Офлайн-база / SSOT)
*   **Функционал:** Локальная БД является Single Source of Truth.
*   **Инвалидация:** При старте фоновый запрос сверяет `updated_at`. Если данные устарели — показывается плашка (без блокировки экрана). При обновлении — пакетная вставка (batch insert) в БД в бэкграунде (изоляте), UI обновляется реактивно через стрим БД.

### 5.4. Арена (Боевой трекер / Encounter)
*   **Функционал:** Управление инициативой, трекинг HP, клонирование монстров.
*   **Слепая зона (Мутации по ссылке):** Добавление 3 одинаковых гоблинов из БД на арену требует паттерна Prototype (глубокое копирование через `.copyWith(instanceId: uuid)`). Если передать объекты по ссылке, урон по одному гоблину вычтет HP у всех трех.

### 5.5. Детализация (Detail View)
*   **Радар характеристик:** `CustomPainter`.
    *   *Контроль:* Инициализация `Paint()` и `Path()` строго в конструкторе пейнтера, вне метода `paint()`.
*   **Интерактивные кубики (Inline Dice):** Парсинг текста атак (RegExp `NdN+N`). Совпадения оборачиваются в `RichText` с обработчиком клика. Результат (рандом + модификатор) выводится в SnackBar.

## 6. Адаптивность экрана (UI/UX)
4 брейкпоинта:
1.  **Mobile Portrait (< 600dp):** Стек навигации. Список и детали — разные экраны.
2.  **Mobile Landscape / Small Tablet (~600–840dp):** Список на весь экран. Детали выезжают как шторка (BottomSheet / EndDrawer).
3.  **Large Tablet (840–1200dp):** Двухколоночный интерфейс. `NavigationRail` + Список (Master) слева, Детали (Detail) справа.
4.  **Desktop (> 1200dp):** Трехколоночный интерфейс. `NavigationRail` -> Список/Арена -> Широкая область деталей.

*Слепая зона:* Использовать `LayoutBuilder` или `MediaQuery.sizeOf(context).width`. Строгий запрет на `MediaQuery.of(context).size` в корне дерева, чтобы появление системной клавиатуры не триггерило ребилд всего приложения.
